# Demo de despliegue: Mis tareas

App mínima de tareas para aprender a desplegar un **frontend + backend + base de datos** en Vercel.
Es una demo de clase: el código es simple a propósito (sin capas extra ni seguridad).

```
Navegador ──► Vercel ──┬── /api/*  ──► backend  (Spring Boot en contenedor) ──► Supabase (Postgres)
                       └── todo lo demás ──► frontend (React + Vite, estático en la CDN)
```

- **frontend/**: React + Vite. En Vercel se construye y se sirve estático desde la CDN.
- **backend/**: Spring Boot 3 (Java 21). En Vercel corre como contenedor a partir de `backend/Dockerfile`.
- **BD**: Postgres de Supabase, tabla `public.tareas`, a través del *Transaction pooler* (puerto 6543).

Front y back comparten dominio (`vercel.json` manda `/api/*` al backend), así que **no hace falta CORS**.
En local, el proxy de Vite (o nginx, si usas Docker) cumple ese mismo papel.

## 1. Base de datos en Supabase

### 1.1 Crear el proyecto

1. Entra a <https://supabase.com> → **New project**.
2. Ponle nombre, elige la región más cercana y **guarda la contraseña de la base de datos** (la vas a necesitar).
3. Espera a que el proyecto termine de crearse.

### 1.2 Crear la tabla

Ve a **SQL Editor** → **New query**, pega esto y dale **Run**:

```sql
create table public.tareas (
  id          bigint generated by default as identity primary key,
  titulo      text        not null,
  completada  boolean     not null default false,
  creada_en   timestamptz not null default now()
);

-- Bloquea el acceso por la API pública de Supabase (clave anon).
-- El backend se conecta como "postgres", así que sigue funcionando.
alter table public.tareas enable row level security;

-- Datos de ejemplo (opcional)
insert into public.tareas (titulo) values ('Preparar la exposición'), ('Desplegar en Vercel');
```

> El backend **no crea ni modifica** la tabla (`spring.jpa.hibernate.ddl-auto=none`): tiene que existir antes.

### 1.3 Obtener los datos de conexión

1. En tu proyecto, botón **Connect** (arriba) → pestaña **Transaction pooler**.
2. Verás una cadena así:

   ```
   postgresql://postgres.abcdefghijk:[YOUR-PASSWORD]@aws-0-us-east-1.pooler.supabase.com:6543/postgres
   ```

3. De ahí salen las **3 variables** que usa el backend:

| Variable | Valor (ejemplo) |
|---|---|
| `DB_URL` | `jdbc:postgresql://aws-0-us-east-1.pooler.supabase.com:6543/postgres?sslmode=require&prepareThreshold=0` |
| `DB_USER` | `postgres.abcdefghijk` (¡con el punto y el id del proyecto!) |
| `DB_PASSWORD` | la contraseña que guardaste en el paso 1.1 |

- `DB_URL` empieza por `jdbc:` y **no** lleva usuario ni contraseña dentro.
- `prepareThreshold=0` es obligatorio con el *Transaction pooler* (no soporta *prepared statements*).
- **Nunca** subas estas credenciales a GitHub. `.env` ya está en `.gitignore`.

## 2. Correr en local (sin Docker)

### 2.1 Backend (terminal 1)

```powershell
cd backend
$env:DB_URL = 'jdbc:postgresql://<host>:6543/postgres?sslmode=require&prepareThreshold=0'
$env:DB_USER = 'postgres.<project-ref>'
$env:DB_PASSWORD = '<tu-password>'
mvn spring-boot:run
```

> Usa **comillas simples** en PowerShell: con comillas dobles, un `$` dentro de la contraseña se pierde sin avisar.
>
> macOS/Linux: `export DB_URL='...'` (igual para las otras dos) y luego `mvn spring-boot:run`.

Cuando veas `Started TareasApplication`, prueba en otra terminal:

```powershell
Invoke-RestMethod http://localhost:8080/api/health
Invoke-RestMethod http://localhost:8080/api/tareas
```

### 2.2 Frontend (terminal 2)

```powershell
cd frontend
npm install
npm run dev
```

Abre <http://localhost:5173>. El proxy de Vite manda `/api` a `http://localhost:8080`.

### 2.3 Solo compilar (sin correr)

```powershell
cd backend;  mvn -q -DskipTests package   # genera backend/target/app.jar
cd ../frontend;  npm run build            # genera frontend/dist/
```

## 3. Correr con Docker

Así ves exactamente lo mismo que en Vercel, pero en tu máquina: dos contenedores en una red de Docker,
con nginx haciendo de "Vercel" (sirve el frontend y reenvía `/api/*` al backend).

Abre **Docker Desktop** y espera a que diga que está corriendo. Todos los comandos se ejecutan **desde la raíz del repo**.

### 3.1 Archivo `.env` con las credenciales

```powershell
Copy-Item .env.example .env
```

Edita `.env` y rellena los valores **sin comillas**:

```
DB_URL=jdbc:postgresql://<host>:6543/postgres?sslmode=require&prepareThreshold=0
DB_USER=postgres.<project-ref>
DB_PASSWORD=<tu-password>
```

### 3.2 Red de Docker (una sola vez)

```powershell
docker network create demo-net
```

### 3.3 Backend: imagen y contenedor

```powershell
docker build -t demo-backend ./backend
```

```powershell
docker run -d --name backend --network demo-net -p 8080:80 --env-file .env demo-backend
```

- Dentro del contenedor Spring escucha en el puerto **80** (igual que en Vercel); `-p 8080:80` lo publica en tu `localhost:8080`.
- `--name backend` es importante: el frontend lo busca con ese nombre dentro de la red.

Comprueba que arrancó (tarda unos 10-15 s):

```powershell
docker logs -f backend          # espera "Started TareasApplication", luego Ctrl+C
Invoke-RestMethod http://localhost:8080/api/health
```

### 3.4 Frontend: imagen y contenedor

```powershell
docker build -t demo-frontend -f frontend/Dockerfile.local ./frontend
```

```powershell
docker run -d --name frontend --network demo-net -p 3000:80 demo-frontend
```

Abre <http://localhost:3000>. nginx sirve la app y manda `/api/*` al contenedor `backend`.

> **Arranca primero el backend**: si el contenedor `backend` no existe, nginx no arranca
> (error `host not found in upstream "backend"`).
>
> ¿Por qué `Dockerfile.local` y no `Dockerfile`? En Vercel el frontend se sirve estático desde la CDN,
> no como contenedor. Con otro nombre evitamos que Vercel lo confunda con un servicio de contenedor.

### 3.5 Comandos útiles

```powershell
docker ps                          # contenedores corriendo
docker logs backend                # ver logs del backend
docker stop frontend backend       # detener
docker start backend frontend      # volver a arrancar (backend primero)
docker rm -f frontend backend      # borrar los contenedores
docker network rm demo-net         # borrar la red
```

Si cambias código, vuelve a hacer `docker build ...`, borra el contenedor viejo (`docker rm -f ...`) y haz `docker run ...` otra vez.

## 5. Desplegar en Vercel

### 5.1 Importar el repo

1. Entra a <https://vercel.com> con **Continue with GitHub**.
2. **Add New… → Project**.
3. En *Import Git Repository* busca tu repo y dale **Import**
   (si no aparece: **Adjust GitHub App Permissions** y dale acceso a ese repo).

### 5.2 Configurar el proyecto

En la pantalla de configuración:

- **Root Directory**: déjalo en la raíz (`./`). **No** elijas `frontend` ni `backend`:
  Vercel lee `vercel.json` y crea los dos servicios solo.
- **Build / Output settings**: no cambies nada.
- **Environment Variables**: agrega las 3 (sin comillas):

| Key | Value |
|---|---|
| `DB_URL` | `jdbc:postgresql://<host>:6543/postgres?sslmode=require&prepareThreshold=0` |
| `DB_USER` | `postgres.<project-ref>` |
| `DB_PASSWORD` | tu contraseña |

Dale **Deploy**. El primer despliegue tarda unos minutos (construye la imagen de Java).

### 5.3 Qué hace `vercel.json`

```json
{
  "services": {
    "frontend": { "root": "frontend/" },
    "backend":  { "root": "backend/", "runtime": "container", "entrypoint": "Dockerfile" }
  },
  "rewrites": [
    { "source": "/api/(.*)", "destination": { "service": "backend" } },
    { "source": "/(.*)",     "destination": { "service": "frontend" } }
  ]
}
```

- **frontend**: Vercel detecta Vite, corre `npm run build` y sirve `dist/` desde la CDN.
- **backend**: Vercel construye `backend/Dockerfile` y corre el contenedor. Escucha en el puerto 80 (`ENV PORT=80`).
- **rewrites**: el orden importa. Primero `/api/*` va al backend (con la ruta completa, `/api` incluido), y todo lo demás al frontend.

### 5.4 Verificar

Cuando termine, abre la URL que te da Vercel (`https://<tu-proyecto>.vercel.app`):

1. `https://<tu-proyecto>.vercel.app/api/health` → `{"status":"ok"}`
   (la primera vez puede tardar unos segundos: el contenedor "despierta").
2. `https://<tu-proyecto>.vercel.app/api/tareas` → la lista en JSON.
3. `https://<tu-proyecto>.vercel.app` → la app. Agrega, marca y borra tareas.

### 5.5 Cambio en vivo (para la demo)

1. Cambia el `<h1>Mis tareas</h1>` en `frontend/src/App.jsx`.
2. `git add . ; git commit -m "Cambio en el título" ; git push`
3. En Vercel → pestaña **Deployments** verás el nuevo despliegue. Al terminar, recarga la página.

### 5.6 Si cambias variables de entorno

**Settings → Environment Variables**, edita el valor y luego **Deployments → ⋯ → Redeploy**.
Las variables nuevas solo se aplican en un despliegue nuevo.

Logs del backend: **Deployments → (el despliegue) → Logs**, o la pestaña **Logs** del proyecto.

## 6. Endpoints y pruebas

| Método | Ruta | Cuerpo | Respuesta |
|---|---|---|---|
| GET | `/api/health` | | `{"status":"ok"}` (no toca la BD; sirve para "despertar" el contenedor) |
| GET | `/api/tareas` | | lista ordenada por id |
| POST | `/api/tareas` | `{"titulo":"..."}` | 201 con la tarea creada · 400 si el título está vacío |
| PUT | `/api/tareas/{id}` | `{"titulo":"...","completada":true}` | 200 · 404 si no existe |
| DELETE | `/api/tareas/{id}` | | 204 · 404 si no existe |

Pruebas rápidas en PowerShell (cambia `$B` por tu URL de Vercel para probar en producción):

```powershell
$B = 'http://localhost:8080/api'
Invoke-RestMethod "$B/health"
Invoke-RestMethod "$B/tareas"
$t = Invoke-RestMethod "$B/tareas" -Method Post -ContentType 'application/json' -Body '{"titulo":"Probar la API"}'
Invoke-RestMethod "$B/tareas/$($t.id)" -Method Put -ContentType 'application/json' -Body '{"titulo":"Probar la API","completada":true}'
Invoke-RestMethod "$B/tareas/$($t.id)" -Method Delete
```

Con curl (macOS/Linux o Git Bash):

```bash
B=http://localhost:8080/api
curl $B/health
curl -X POST -H "Content-Type: application/json" -d '{"titulo":"Probar la API"}' $B/tareas
```

## 7. Problemas comunes

| Síntoma | Causa probable | Solución |
|---|---|---|
| `password authentication failed for user "postgres"` | contraseña mal escrita o usuario sin el id del proyecto | usa `postgres.<project-ref>`; en PowerShell usa comillas simples; o resetea la contraseña en Supabase (**Project Settings → Database**) |
| `Tenant or user not found` | `DB_USER` sin el `.<project-ref>` | copia el usuario exacto de **Connect → Transaction pooler** |
| `prepared statement "S_1" already exists` | falta `prepareThreshold=0` en `DB_URL` | agrégalo al final de la URL |
| `/api/health` va bien pero `/api/tareas` da 500 | el backend no llega a la BD | revisa las 3 variables y los logs (`docker logs backend` o Logs en Vercel) |
| La app dice "No se pudo conectar con la API" | backend apagado o todavía arrancando | arranca el backend; en Vercel espera unos segundos y recarga |
| La primera petición en Vercel tarda | arranque en frío del contenedor | normal; abre `/api/health` antes de la demo |
| `host not found in upstream "backend"` (nginx) | el contenedor `backend` no está corriendo | arranca primero el backend (sección 3.3) |
| `port is already allocated` / puerto en uso | otro proceso usa 8080, 3000 o 5173 | detén ese proceso o cambia el puerto de la izquierda en `-p` |
| Cambié variables en Vercel y no pasa nada | no se volvió a desplegar | **Redeploy** (sección 5.6) |
